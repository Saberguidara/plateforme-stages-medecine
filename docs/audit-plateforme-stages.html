Audit technique · 30 octobre 2026

Plateforme des fiches de validation de stage

Angular 21 + Express 5 + MySQL. Audit du code, tests de sécurité et de charge réalisés sur la base locale (707 résidents, 3 421 fiches), et proposition d'un déploiement gratuit en une seule URL.

Dépôt : Saberguidara/plateforme-stages-medecineCommit : a9b52f6

Verdict

Pour un projet de 2ᵉ année, la base est saine : requêtes SQL paramétrées, JWT, bcrypt, helmet, rate limiting, transactions sur l'import, tests Jest. Le projet ne doit pas être mis en ligne tel quel : deux failles permettent de produire de fausses fiches officielles et de prendre le compte de presque n'importe quel résident.

1Sécurité du code et des accès

Chaque point critique a été vérifié en exécutant le serveur, pas seulement en lisant le code.

Critique

N'importe quel connecté peut générer une fiche officielle falsifiée

controllers/pdf.controller.js · POST /api/generate-pdf

Le serveur fabrique le PDF à partir du nom, de la spécialité, de l'hôpital et du service envoyés par le navigateur, sans rien comparer à la base. Test réalisé : avec le jeton d'un résident au CIN inexistant « ZZZ », le serveur a renvoyé une fiche de 116 Ko au nom de « PERSONNE INVENTEE », CHU Fictif, 5ᵉ année.

Correctif : la route reçoit uniquement ficheId, relit la fiche et le résident en base, et vérifie que la fiche appartient au résident connecté (ou que l'appelant est admin).

Critique

Prise de compte par « premier e-mail arrivé »

controllers/auth.controller.js · requestOTP

Si le résident n'a pas encore d'e-mail en base, le premier qui saisit son CIN choisit l'adresse qui recevra le code, et elle est enregistrée définitivement. Or 705 résidents sur 707 n'ont pas d'e-mail. Un CIN (imprimé sur beaucoup de documents) suffit pour s'approprier le dossier et bloquer le vrai résident.

Correctif : importer l'e-mail depuis la liste officielle de la faculté (colonne Excel) ou faire valider l'association CIN/e-mail par l'admin. Ne jamais lier un e-mail sur simple déclaration.

Critique au déploiement

Le rate limiting deviendra global derrière Render

server.js · absence de app.set('trust proxy', 1)

Derrière un proxy (Render, Koyeb…), Express voit l'IP du proxy pour toutes les requêtes. Résultat : 5 connexions admin par 15 min et 10 PDF par minute pour toute la faculté. Le jour de la remise des fiches, presque tout le monde recevra « Trop de requêtes ».

Correctif : une ligne, app.set('trust proxy', 1), puis limiter aussi par compte (CIN), pas seulement par IP.

Élevée

OTP faible et code de demande non limité

auth.controller.js · auth.routes.js

Le code est généré par Math.random() (non cryptographique), stocké en clair, sans compteur d'essais par compte. /login/request-otp n'a aucun limiteur : 30 requêtes d'affilée sont toutes passées, et la réponse 404 « Résident introuvable » permet de tester quels CIN existent.

Correctif : crypto.randomInt, code haché, blocage après 5 essais par CIN, limiteur sur la demande, et message neutre (« Si ce dossier existe, un code a été envoyé »).

Élevée

« Annuler l'import » supprime ce que le navigateur demande

controllers/import.controller.js · undoImport

Les CIN et identifiants à supprimer viennent du corps de la requête. Une erreur ou un onglet resté ouvert peut effacer des résidents antérieurs ; leurs fiches restent alors orphelines (pas de suppression en cascade, pas de transaction). La table historique_imports existe mais n'est pas utilisée.

Correctif : enregistrer l'import côté serveur et annuler par importId, dans une transaction, avec une clé étrangère ON DELETE CASCADE.

Élevée

22 vulnérabilités connues côté backend, 11 côté frontend

npm audit --omit=dev

Dont xlsx 0.18.5 (pollution de prototype et ReDoS, aucun correctif sur npm), précisément la librairie qui lit les fichiers Excel envoyés.

Correctif : passer à exceljs ou au paquet SheetJS officiel 0.20.x, puis npm audit fix.

Élevée

Aucun schéma SQL versionné

docs/database-schema.md

Impossible de recréer la base sur un hébergeur sans exporter à la main depuis WAMP. C'est l'une des causes de la difficulté de déploiement.

Correctif : ajouter backend/db/schema.sql (tables, clés étrangères, index) et un script npm run db:init.

Moyenne

Points secondaires

  • Mot de passe admin en clair encore accepté (modification non commitée) : utile pour migrer, à retirer ensuite.
  • /uploads et /api/files/:name sont publics et sans authentification ; le dossier n'existe plus : code mort à supprimer.
  • L'erreur d'import renvoie error.message brut au client.
  • requireResident ne vérifie pas role === 'resident'.
  • Les logs (backend/logs/*.log) sont versionnés dans Git : à ignorer.
  • Pool MySQL à 50 connexions : les bases gratuites en acceptent souvent 10 à 25. Passer à 5–10.

  • Lecture résident : largement suffisante pour toute la promotion connectée le même jour.
  • Liste admin : une sous-requête COUNT par ligne, plus un tri sur ce calcul. Un LEFT JOIN … GROUP BY la rend environ 10 fois plus rapide. Usage admin seulement, donc non bloquant.
  • PDF : chaque fiche lance une page Chromium (~1 s, ~200–300 Mo de RAM). Sur une offre gratuite à 512 Mo, Puppeteer risque de faire planter le serveur. Le remplacer par pdf-lib ou pdfkit donne des fiches en ~50 ms avec quelques Mo, et rend le déploiement gratuit fiable.
  • Index : residents.cin est indexé trois fois et formulaires_stage.resident_id deux fois de trop. Cela ralentit l'import sans rien apporter.

3Critique UX/UI

Ce qui marche

  • Page de connexion soignée, identité FMSfax claire sur ordinateur.
  • Parcours OTP compréhensible, compte à rebours, 429 géré sans message d'erreur brutal.
  • Tri des fiches dans l'ordre réel du cursus (T1, T2, S1…).
  • Admin : pagination, filtres, annulation d'import.

À corriger en priorité

  • Mobile : sur un téléphone de 375×812, le premier champ est à 846 px, sous la ligne de flottaison. Les résidents ouvriront le lien sur leur téléphone et verront une grande image floue sans formulaire.
  • Icônes invisibles : les classes bi-eye, bi-download sont utilisées mais Bootstrap Icons n'est pas chargé.
  • Double clic : isGenerating ne désactive pas les boutons, ce qui relance des PDF et déclenche le limiteur.
  • Champ OTP : ajouter inputmode="numeric" et autocomplete="one-time-code" pour le pavé numérique et le remplissage automatique.
  • Contraste : texte orange sur fond beige (environ 2,6:1) sous le minimum WCAG de 4,5:1.
  • Tableau des fiches à 6 colonnes : sur téléphone, passer en cartes (période, hôpital, bouton Télécharger).
  • « Aperçu » ouvre un onglet après un appel asynchrone : bloqué par Safari iOS. Afficher le PDF dans la page ou ne garder que Télécharger sur mobile.
  • Animations lourdes (flous, pulsation infinie) sans prefers-reduced-motion : coûteux sur les téléphones d'entrée de gamme.
  • Un serveur gratuit met jusqu'à une minute à se réveiller : prévoir un message « Démarrage du serveur… » plutôt qu'un échec silencieux.

4Architecture et qualité du code

  • Bon découpage routes / contrôleurs / middlewares / services, validation centralisée.
  • Bug : updateResident ignore la spécialité envoyée.
  • Suppression d'un résident en deux requêtes sans transaction.
  • Front : express et @angular/platform-server installés mais inutilisés (restes de SSR) ; plusieurs composants appellent HttpClient directement au lieu de passer par ApiService.
  • URL de l'API codée en dur dans environment.prod.ts : avec un seul serveur, elle devient simplement /api.
  • Tests : 15 tests passent, mais aucun ne couvre l'OTP, la génération de PDF ou l'import.

5Déploiement gratuit, une seule URL

La difficulté venait du découpage : front sur Netlify, API sur Render, base ailleurs, avec CORS et deux URL à synchroniser. La solution est de faire servir l'application Angular compilée par le serveur Express lui-même. Une seule application, une seule URL, plus de CORS, et un déploiement automatique à chaque git push.

A · Render + MySQL gratuit Recommandé

  • Un seul service Render, connecté au dépôt GitHub.
  • Base MySQL gratuite chez Aiven (ou TiDB Cloud, compatible MySQL) : le code SQL reste identique.
  • Deux comptes au lieu de trois, configurés une fois ; ensuite tout passe par git push.
  • Limite : le service s'endort après 15 min d'inactivité (réveil 30–60 s).

B · Une VM gratuite (Oracle Always Free)

  • Tout sur une machine via Docker Compose : app + MySQL.
  • Pas de mise en veille, une seule plateforme.
  • Demande une carte bancaire à l'inscription et l'administration d'un serveur Linux (mises à jour, HTTPS, sauvegardes).
  • Trop lourd pour un débutant ; à envisager plus tard.

Les limites des offres gratuites changent souvent : je les vérifierai sur les sites officiels au moment de créer les comptes. Pour un usage officiel durable, demander à la faculté un petit hébergement ou un sous-domaine reste la meilleure option à terme.

6Plan d'action

  1. Corriger les trois failles critiques

    PDF généré depuis la base uniquement, liaison e-mail sécurisée, trust proxy. OTP renforcé et limiteurs dans la foulée.

  2. Remplacer Puppeteer par pdf-lib

    Fiche identique, ~20 fois plus rapide, compatible avec une offre gratuite à 512 Mo.

  3. Fusionner front et back en une application

    Express sert le build Angular, API sur /api, script npm run build unique à la racine.

  4. Versionner le schéma SQL

    schema.sql + script d'initialisation, nettoyage des index en double, clés étrangères.

  5. Corrections UX mobiles

    Formulaire visible dès l'ouverture, icônes, boutons désactivés pendant la génération, champ OTP numérique, cartes sur mobile.

  6. Mettre à jour GitHub et déployer

    Commit propre (sans logs ni secrets), création de la base gratuite, du service Render, puis lien final à donner aux résidents.
